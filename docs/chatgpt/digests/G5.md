### 40 - Keyboard velocity processing (outside project; shared link) - 2025-10-15 to 2026-01-03  [MAIN MIDIBOX CHAT]
Reverse-engineering the dead SL88's Fatar keybed "STM32 scanner board" and turning its odd serial stream into usable USB MIDI on a Pico W. Arc: sniff UART (only saw note on/off) -> 10 nF cap + inverted velocity found -> STM32 board photo breakdown -> Pico CircuitPython monitor/tuner -> Pi 4 port -> discovery that the stream is not normal MIDI (channel nibble carries velocity MSBs, inverted) -> failed attempts to talk to the board (kick, enable line, SysEx probes, SPI replay "Plan C") -> "Plan A" (receive-only + nibble-hack velocity reconstruct) works -> Pico W final with curves + sustain -> web UI / macOS menubar ideas -> Nov 2025 expression pedal on GP26 -> Jan 2026 sustain pedal intermittently crashes Pico.

**Hardware facts**
- Keybed: user says 3-contact Fatar, "TP10 (i think)", 88 keys. Normal Fatar theory given: two contacts per key, A (early) then B (late), velocity = f(delta t); typical 2-12 ms; third contact sometimes release velocity; aftertouch strip is resistive/analog. Midibox spec says Fatar has Aftertouch + Velocity + 88 keys.
- The ex-SL88 "slave" board has an STM32F103C8T6 (inferred from photo), 8 MHz crystal, 3.3 V regulator (U2), three flat-flex keybed connectors J2/J4/J5, 4.7k (472) pullups, U1 16-pin SOIC mux (inferred, 74HC4051/138 guess), three 6-pin white headers, small 4-pin JST (maybe aftertouch/sustain, unconfirmed). Firmware believed locked (RDP not checked; SWD dump never attempted).
- Master/main board <-> STM32 link is 3 wires: user colour code yellow, blue, white.
  - Yellow = STM32 TX / the note data to the Pico (confirmed by user). Runs at 31,250 baud 8N1, idle high, ~32 us/bit (KingstVIS logic analyzer capture).
  - White = pulling it low (10k to GND) stops the stream -> assumed ENABLE/reset-like line, keep HIGH (inferred; pulse low 50-100 ms then send kick).
  - Blue = 10k to GND did NOT stop the stream -> assumed command line into STM32 (Pico TX).
  - Pulling either of blue/white hard low stopped notes before the 10k test.
- At power-up the main board and STM32 talk over what looks like SPI (three wires active: SCLK, MOSI, MISO) for roughly the first ~2 s, MOSI/MISO bytes mostly 0xFF with odd 0xDF/0xBF/0xFB; main board powered on at ~800 ms in the user's capture; then clock idles and the former MOSI wire carries UART 31,250 note data (assistant's interpretation, unproven). A standalone capture of the main board's power-up: 0x00 when off, then 0xFF,0x00,0xFF,... pairs (FF + data byte) every 20-40 ms.
- "Kick": a single 0x00 byte at 31,250 on the command UART wakes the STM32 to send notes (user-found; one variant sent b"\x02" during tests). Config in code: KICK_MODE uart/gpio/none, KICK_BYTES b"\x00", GPIO kick pin GP19.
- Stream format (the key finding): Note On/Off frames are 3 bytes but the "channel" low nibble of byte 1 is NOT a channel. It tracks velocity inverted (harder press = lower nibble, soft ~0x7F/high nibble) and byte 3 is noisy/limited. Example captures: 0x9F 0x3C 0x7F (lightest), 0x98 3C 01, 0x93 3C 2D, 0x92 3C 42, 0x91 3C 43/16/29, 0x90 3C 6F (hardest); Note-Off frames 0x88..0x82 with release-velocity bytes 0x35,0x51,0x43,0x2C,0x3D,0x5D,0x10,0x66. Note numbers sequential (0x15 = A0 = 21 at bottom). Without a fixed channel the Note Offs went to different channels -> stuck notes on synths.
- Capacitor: 10 nF added on the data line made velocity "stable but inverted"; SN74HC14N Schmitt triggers "didn't change anything" (see chat 15).
- Plan A velocity reconstruct (the working method): msb = 15 - (status & 0x0F) (INVERT_MSB=True); velocity = (msb << 3) | (byte3 & 0x07) with LSB_BITS=3 (alt LSB_BITS=4: (msb<<4)|(byte3&0x0F)); clamp 0..127; Note On vel 0 -> Note Off; force channel 1. Source modes: reconstruct | raw (byte3 & 0x7F) | fixed (FIXED_VELOCITY=100). Curves LUT: raw, linear, hard (gamma 0.6), soft (gamma 2.2), s_curve, exp, log, pow; OUT_MIN=10, OUT_MAX=110. User's final feel: "Exponential and upped the curve a little" (exact CURVE_PARAM not stated; default 2.2). RELEASE_MODE "same".
- Pico W wiring (CircuitPython 10.x, usb_midi out): STM32 yellow -> GP5 (UART1 RX, 31,250, buffer 2048); common GND; sustain pedal GP16 -> pedal -> GND with internal pull-up (PEDAL_POLARITY "normally_open" or "normally_closed", debounce 10 ms, sends CC64 127/0). Expression pedal: Tip -> GP26 (A0/ADC0), Ring -> 3V3, Sleeve -> GND, CC11. Earlier dev wiring: UART0 RX GP1, UART1 TX GP4/RX GP5, PWM clock GP18 (1 kHz 50%), kick GP19, 10k->GND tests.
- Pi 4 wiring used for Plan A/sniffing: STM32 TX -> Pi GPIO15 (RXD, pin 10), GND, optional TX GPIO14 (pin 8), enable on GPIO17 (pin 11); Pi 4 UART on /dev/serial0 -> ttyS0 (mini-UART) because Bluetooth keyboard needed ttyAMA0; config.txt enable_uart=1 under [all]. Pi 4 script "pi_uart_plan_a.py" creates ALSA virtual port "PiKeybed Out" (mido). Plan A "works perfect" on Pi 4 (21 Oct 2025 22:22), then was ported to Pico W.
- Nov 2025: user recalled "Pi pin 5 -> plug pin 3 and sustain 15 -> GND"; ChatGPT confirmed as Pi pin 5 (GPIO3/SDA1) -> keyboard plug pin 3 data and sustain on GPIO15 (pin 10). This is inconsistent with the Pico code (RX GP5, pedal GP16) -- treat the Pico code as authoritative; the Pi-pin statement is unreliable. Pico physical pin 5 is GP3 (not used by the code).
- Pico RP2040 throughput: with scaling off, 8 simultaneous notes dropped the low notes in the first tuner; fixed by draining in_waiting each loop, batching USB writes, no prints in hot path (monitor off by default). Full polyphony then reported OK in Plan A.
