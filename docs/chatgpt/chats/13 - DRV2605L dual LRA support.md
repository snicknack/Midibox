Excellent question — and a *critical one* for the SuperCore.  

👉 **Short answer:**  
The **DRV2605L cannot directly drive two LRAs** simultaneously — it’s strictly **a single-channel haptic driver**.  

---

### 💡 Why
- The **DRV2605L** has **one output stage (OUT+)**, meant to drive **one ERM or LRA actuator** at a time.  
- Internally, it uses a closed-loop driver (for LRAs) that constantly measures back-EMF to tune resonance.  
  If you attach **two LRAs**, their mechanical resonances interfere and confuse the feedback loop, causing:
  - weak vibration,
  - distorted frequency,
  - or outright failure to start oscillation.

---

### 🧩 Your options

#### 1️⃣ Use **two DRV2605Ls**
- Easiest and most robust method.  
- Each LRA gets its **own driver IC and I²C address** (default 0x5A).  
- You can reassign one by tying **A0 to VDD** or **GND**:  
  - A0 = GND → `0x5A`  
  - A0 = VDD → `0x5B`  
- Then you control both:
  ```python
  haptic1 = DRV2605(i2c, address=0x5A)
  haptic2 = DRV2605(i2c, address=0x5B)
  haptic1.sequence[0] = 47
  haptic2.sequence[0] = 48
  haptic1.play()
  haptic2.play()
  ```

#### 2️⃣ Use **one DRV and alternate** between two LRAs
- You can technically **multiplex** the output using an analog switch (e.g. **CD4053** or **74HC4053**).  
- But you’d have to:
  - disable the driver (`MODE` = standby),
  - switch the output to the second LRA,
  - re-calibrate the resonance,
  - then trigger playback.  
- Not suitable for fast or simultaneous tactile feedback — too slow and complex.

#### 3️⃣ Use a **multi-channel driver**
If you want synchronized dual feedback (say, left/right encoder tactile cues), look at:
- **DRV2606/07** → also single-channel, similar limits.  
- **DRV2624** → 2-channel *audio input capable*, can be configured for dual LRA.  
- **DRV8910** series (multi-channel motor drivers) → can do open-loop vibro but not closed-loop LRA control.  
- **Custom MCU PWM control** → drive small LRAs in open-loop mode using DAC or PWM and op-amp buffer (less precision).

- **One LRA per encoder** → use **one DRV2605L per LRA** (each on unique address).

### 🔧 I²C electrical rule
All I²C devices share the same **SDA** (data) and **SCL** (clock) lines in **parallel**.  
Each device listens for its own address — so all SDA/SCL pins connect together like this:

```
          +-----> [ ADS1115 ]
          |
PI SDA ---+-----> [ SX1509 ]
          |
          +-----> [ DRV2605L ]
          
PI SCL ---+-----> [ ADS1115 ]
          |
          +-----> [ SX1509 ]
          |
          +-----> [ DRV2605L ]
```

This is a **bus**, not a chain — signals fan out to each module.  

---

### 🧩 So the correct wiring is:
| Pi | ADS1115 | SX1509 | DRV2605L |
|----|----------|--------|----------|
| SDA (GPIO2) | SDA | SDA | SDA |
| SCL (GPIO3) | SCL | SCL | SCL |
| 3V3 | VDD | VCC | VIN |
| GND | GND | GND | GND |

Every SDA connects together, every SCL connects together, all powered from the same 3V3/GND rail.  
That’s it — parallel wiring.

---

- You only need **one pair of pull-up resistors** (to 3.3 V).  
  - Most breakout boards already include 4.7 kΩ pull-ups on SDA/SCL — if *multiple* boards have them, that’s fine for small setups.
- Keep total cable length short (< 30 cm ideally).
- Each device must have a **unique address** (`ADS1115` default `0x48`, `SX1509` default `0x3E`, `DRV2605L` `0x5A`).

✅ Parallel = correct  
❌ Daisy-chain (SDA→next SDA-out→next) = wrong for I²C

### So what do you need on a productized module?
Two viable architectures:

## A) “Thin” peripheral (no local MCU)
- **Parts:** Encoder + WS2812 ring + DRV2605L + I²C pull-ups + passives.
- **Interface to host:** I²C for the DRV2605L; a **separate LED data line** (from host) for the NeoPixel ring; encoder pins go to host GPIO (or via an I/O expander like SX1509).

- **Add a tiny MCU** (ATtiny / STM32G0 / RP2040).

  - Drive **DRV2605L** over I²C (tick/press/end-stop effects).

  - Expose a **clean protocol** upstream (I²C or UART; optional USB-MIDI later).
- **Pros:** One cable (5 V + GND + 2 wires for I²C/UART), buttery LED timing, consistent haptics, firmware-upgradable, drop-in module.  
- **Cons:** Slightly higher BOM + firmware to maintain.

- **5V, GND**

class RingMeter:
    def __init__(self,
                 pin=PIN,
                 num_pixels=NUM_PIXELS,
                 brightness=BRIGHTNESS,
                 mode=MODE,
                 top_offset=TOP_OFFSET,
                 vmin=VMIN, vmax=VMAX,
                 pixel_order=PIXEL_ORDER,
                 bpp=BPP,
                 color=RING_COLOR):

        self.mode = mode

            self.n,
            brightness=brightness,
            auto_write=False,
            pixel_order=pixel_order,
            bpp=bpp

        span = max(1, (self.vmax - self.vmin))

        else:  # "dot"
